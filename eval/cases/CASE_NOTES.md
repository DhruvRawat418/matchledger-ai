# Method-ladder cases (case-101 … case-105)

Five synthetic cases, one per matching/handling level. Generated by
`python -m eval.make_sample_cases`; Dhruv renders the PDFs from each case's
`documents` section. ✔ = expected to succeed, ✘ = expected to fail, (✔) =
should succeed but is at risk.

## The dividing line between fuzzy and LLM

Apply our fixed cleaning rules to both descriptions. If the cleaned strings
are (nearly) identical — "STRAWBERRY_BANANA_SB 2LB" vs "Strawberry Banana
Smoothie Mix, 2 lb" — the line is **formatting** and belongs to the
cleaned/fuzzy level. If pairing them requires knowing that different words
name the same product — "24-inch LED screen" vs "Display, 24 in" vs
"24in Monitor" share only the token "24" — the line is **synonym** and
belongs to the LLM level. `EXPECTED_BY_CATEGORY` in `eval/ground_truth.py`
encodes this per line tag, so the scorer can check each method against its
predicted behaviour automatically.

## What each matching method should do per case

| Case | Exact | Cleaned/fuzzy | LLM | What decides it |
| --- | --- | --- | --- | --- |
| 101 exact | ✔ | ✔ | ✔ | SKUs everywhere, identical text |
| 102 fuzzy | ✘ | ✔ | ✔ | Only formatting separates descriptions |
| 103 llm | ✘ | ✘ | (✔) | True synonyms; a look-alike invites a wrong match |
| 104 human error | ✔ | ✔ | ✔ | Matching trivial; invoice handling is tested |
| 105 human error | ✔ | ✔ | ✔ | Matching trivial; receipt handling is tested |

## case-101 — fully correct (the control case)

- No errors planted. Expected status: `clean` on revision 1.
- Tests **false alerts and false matches**: every discrepancy or unmatched
  line any method reports here counts against it.

## case-102 — formatting noise (cleaned/fuzzy level)

- Planted errors: paper overbilled (5.95 vs PO 5.10) and short-delivered
  (30 of 40). Expected: `needs_review` with `price_mismatch` + `quantity_mismatch`.
- Exact match fails on every supplier line (case, underscores, `_SB` / `-NEW`
  suffixes, spacing) → it should report unmatched lines and *miss both real
  errors*. Cleaned matching recovers the lines and must then find both errors.

## case-103 — semantic mismatch (LLM level)

- PO says "24in Monitor" (MON-24); the invoice bills "Display, 24 in"; the
  delivery note says "24-inch LED screen". The laptop is billed as "14in
  laptop" against PO "Notebook computer, 14 inch".
- Planted error: laptop overbilled (949.00 vs PO 899.00). Expected:
  `needs_review` with one `price_mismatch`.
- Exact and cleaned matching are *expected to fail* here — that is the point
  of the comparison. A method that can't pair the lines also can't see the
  price error sitting on them.
- Look-alike trap: "Monitor, 27 inch" must go to MON-27, not MON-24. A wrong
  match creates false alerts — this is where the LLM's precision is at risk,
  and flagging `uncertain` for review is the acceptable outcome.

## case-104 — human error: duplicate + conflicting invoice (4 revisions)

Matching is deliberately trivial (SKU `CHR-STD` on every document) so only
document handling is tested:

| Rev | Event | Expected status | Expected discrepancies |
| --- | --- | --- | --- |
| 1 | Invoice bills 47.50 vs PO 45.00 | needs_review | price_mismatch |
| 2 | Same invoice accidentally uploaded twice | needs_review | duplicate_document (identical copies) + price_mismatch |
| 3 | Corrected invoice uploaded, original left in place | needs_review | duplicate_document (conflicting versions) + price_mismatch |
| 4 | Original retired; only corrected invoice current | clean | none |

Failure modes tested: paying twice (rev 2), reconciling against the wrong
version (rev 3), flags not clearing once resolved (rev 4).

## case-105 — human error: duplicate delivery note (3 revisions)

| Rev | Event | Expected status | Expected discrepancies |
| --- | --- | --- | --- |
| 1 | PO + invoice + delivery note; all agree (10/10/10) | clean | none |
| 2 | Same delivery note DN-7701 uploaded twice | needs_review | duplicate_document |
| 3 | Duplicate retired | clean | none |

The trap: naively summing receipts shows 20 received against 10 ordered. The
correct flag is `duplicate_document`; an over-delivery `quantity_mismatch`
here is a **false alert** and is scored as one.

## Conventions fixed in these cases

- `duplicate_document` discrepancies carry `expected: null, observed: null`;
  the conflicting amounts go in the explanation. (Numeric expected/observed
  are reserved for quantity/price codes.)
- Duplicates are recognizable by `business_document_number`: the same number
  current on two documents ("INV-9901" twice, "DN-7701" twice).

## For Dhruv — integration points when converting these to PDFs

1. **Print the business document number on every PDF** (INV-9901, DN-7701…).
   Duplicate detection in cases 104/105 depends on extracting it. Also decide
   who owns the duplicate check: intake/orchestrator or reconciliation.
2. **Upload order = revisions.** Each case's `revisions[].event` says which
   file arrives when; the eval harness replays uploads in that order and
   compares after each one. The orchestrator must re-stamp all current
   documents with the new case revision (per DATA_CONTRACTS).
3. **Retiring a document** (case-104 rev 4, case-105 rev 3) needs an intake or
   review action — currently no contract covers it. With Maia: does upload ask
   "is this a correction/duplicate?", or does review resolve it afterwards?
4. **Document IDs**: ground truth uses internal IDs (`case-104-inv-9901a`);
   intake assigns real IDs at upload. Name each PDF after its ground-truth
   `document_id` so the harness can map uploads to expected documents.
5. **Receipts show no prices and no currency** — delivery-note template must
   omit the price column (`currency: null` per contract).
6. **Evidence text**: render each line so the ground-truth `evidence[].text`
   actually appears on the page (one page per document, `page: 1`), so
   extraction evidence can be checked against the ground truth.
7. **`method` enum**: contracts allow `exact | fuzzy | llm | human`. Our
   middle method is cleaning + direct match — agree whether it reports as
   `fuzzy` or we add `normalized` to the contract.

## Scoring reminders

- Match accuracy is scored per line against `expected_matches`
  (decision + selected_po_line only), reported by `line_tags` category and
  checked against `EXPECTED_BY_CATEGORY` per method.
- Final-case correctness is scored per revision against
  `expected_reconciliation` (status + discrepancy codes on the right lines).
- 101 (and 105 rev 1) contribute precision (false alarms); 102/103 contribute
  recall (missed errors); 104/105 contribute revision and duplicate handling.
